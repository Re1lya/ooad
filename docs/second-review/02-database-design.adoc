== 设计原则

* ER 图只表达核心业务对象及其关系，不画日志、会话、Token 等技术对象（第一轮检查意见）。
* 用户—角色、角色—前端权限、前端权限—API 资源三组关系均为多对多；角色继承是角色到角色的多对多自关联。
* 统一会话不建会话表：令牌携带身份、凭证版本与有效期，服务端每次请求都核对账号状态与凭证版本；停用、改密、退出时凭证版本加一，该用户在所有系统的令牌同时失效（FR-39）。
* 部署使用 MySQL 8，应用以 `ddl-auto=validate` 启动，表结构由 link:../first-review/database-mysql.sql[建表脚本] 创建。

== 概念模型（核心 ER）

六类核心概念：用户、部门、应用、角色、前端权限（菜单/按钮）、API 资源。

image::er-core.png[核心概念 ER,800]

[cols="2,1,4",options="header"]
|===
|关系 |基数 |说明
|部门—用户 |1:N |部门树（自关联 1:N）；用户可不属于部门
|用户—角色 |M:N |`sys_user_role`；多角色权限取并集
|角色—角色（继承） |M:N |`sys_role_hierarchy`；高级角色获得被继承角色的权限，DAG，多级多继承
|角色—前端权限 |M:N |`sys_role_permission`；以节点为单位授权
|应用—前端权限 |1:N |菜单树（自关联 1:N），按钮挂在同应用菜单下
|应用—API 资源 |1:N |方法 + 路径 + 应用唯一；可登记后端权限码
|前端权限—API 资源 |M:N |`permission_api`；菜单/按钮调用的后端接口，两端同应用
|===

== 本轮变更

[cols="2,4",options="header"]
|===
|变更 |原因
|`api_resource.code` |课程系统按后端权限码（`TC`、`CV` 等）做方法级授权；权限码登记在 API 资源上，经“前端权限—API”绑定随角色下发。一个权限码可覆盖多个接口（`TCM` 同时覆盖 `PUT`、`DELETE /current-term`），因此不设唯一键
|`sys_audit_log` |课程系统把关键操作写入统一身份系统并从中查询（老师课程系统的既有契约）；本系统也记录角色继承变更
|===

== 一致性与并发

* 唯一键保证三组关联与继承边不重复，重复请求在服务层表现为幂等。
* 多级防环在服务层完成：写继承边前对角色表加悲观写锁（`RoleRepository.lockHierarchyRoles` / `RoleCatalog.lockGraph`），在同一事务内读取全图后校验，避免并发反向加边形成环（`PhaseTwoRbac1Tests.FR18_concurrentOppositeEdgesCannotFormCycle`，在真实 MySQL 上运行）。
* 删除被引用的角色、权限、资源、应用返回 409。

== 验证

* 自动化测试连接真实 MySQL：每个 Spring 上下文启动时执行本建表脚本，Hibernate 以 `ddl-auto=validate` 启动，核对每张表的列与类型；`MySqlSchemaTests.NFR03_deploymentDdlMatchesEntityConstraints` 再核对主键、唯一约束、外键（14 个）与检查约束和实体声明一致。
* 服务器上的 MySQL 用同一份脚本建库，两种设计模式都以 `ddl-auto=validate` 启动并通过公网联调核对，见 link:05-deployment.adoc[部署说明]。
