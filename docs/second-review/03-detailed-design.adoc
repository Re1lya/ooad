== 总体结构

系统是一个 Spring Boot 单体，两种设计实现同一组 HTTP 契约与同一个数据库，启动时由 `app.backend-strategy=structured|ddd` 条件装配（`@ConditionalOnProperty`）。`GET /api/system-info` 返回每个业务模块实际装载的实现。

调用链：

* 结构化：`Controller → UseCase 端口 → 结构化 Service（事务脚本） → Spring Data Repository → 表`
* DDD：`Controller → UseCase 端口 → DDD 应用服务 → 领域对象 / 领域仓储端口 → JPA 适配器 → Spring Data Repository → 表`

[[包图]]
=== 包图

包结构统一为“先分层后分模块”：顶层按层（`controller`、`dto`/`vo`、`service`、`infrastructure`、`repository`、`entity`），层内按功能模块分包；`service` 层内部并列三部分：用例端口 `service.port`、结构化实现 `service.<模块>`、DDD 实现 `service.ddd.application` / `service.ddd.domain`。

image::package-overview.png[后端包图,1000]

依赖规则（由 `DualDesignBoundaryTests` 自动检查）：

* `controller` 只依赖 `service.port` 中的用例接口，不引用任何具体实现或 JPA 实体；
* `service.ddd.application` 与 `service.ddd.domain` 不依赖 `repository`、`entity`、`jakarta.persistence`、`org.springframework.data`；
* JPA 适配器（`infrastructure.persistence`）实现领域仓储端口，是唯一把实体转换为领域对象的地方（CloneFactory）。

== 面向对象的 DDD 设计

=== 领域模型与分层

[cols="1,2,4",options="header"]
|===
|层 |包 |职责
|接口层 |`controller.*` |HTTP 协议、DTO 校验、映射为用例输入
|应用层 |`service.ddd.application.*` |用例编排、事务边界、加载与保存领域对象；不写业务规则
|领域层 |`service.ddd.domain.model` |实体、值对象、领域服务维护业务规则；无 Spring/JPA 依赖
|领域仓储端口 |`service.ddd.domain.repository` |面向领域对象的仓储接口
|基础设施层 |`infrastructure.persistence` / `security` / `logging` |JPA 适配器、凭证与路径匹配、当前操作人、分层日志
|===

[cols="2,1,4",options="header"]
|===
|领域对象 |类型 |职责
|`AccessRole` |实体 |角色编码、名称、启停状态
|`Account` |实体（聚合根） |账号可用性（启用 + 有效期）、凭证版本、资料与状态规则
|`ManagedSystem` |实体 |应用编码与启停
|`FrontendPermission` / `PermissionDirectory` |实体 / 领域服务 |菜单按钮树、祖先可用性、导航与授权区分
|`ProtectedResource` |实体 |API 方法 + 路径 + 后端权限码；`authorityCode()` 自己判断是否提供权限码
|`RoleGraph` |值对象（不可变） |角色继承图：防环 `assertCanInherit`、有效路径 `effectivePaths`
|`AuthorizationSnapshot` |领域服务 |一次请求内的授权快照：有效角色、有效权限、来源与路径
|`AssignmentRepository` 等 7 个仓储端口 |仓储 |用户角色、角色权限、权限 API、继承边与各目录的读写
|===

== 结构化设计与 DDD 的区别（答辩要点）

[cols="1,3,3",options="header"]
|===
|对照点 |结构化（面向功能） |DDD（面向对象）
|模型中心 |数据流与处理步骤：DFD → 模块结构图 |业务领域与统一语言：角色、继承图、授权快照
|规则放在哪里 |服务方法里的过程代码（`RoleHierarchyService.inherit` 按步骤校验） |领域对象自身（`RoleGraph.assertCanInherit`、`Account.usable`、`ProtectedResource.authorityCode`）
|数据访问 |服务直接用 Spring Data Repository 和 JPA 实体 |应用服务只依赖领域仓储端口，JPA 适配器转换实体与领域对象
|变化的边界 |按步骤拆模块；换存储或算法要改服务过程 |按概念与不变量封装；换存储只换适配器，规则不动
|评价方法 |耦合、内聚、深模块、信息隐藏 |聚合边界、职责分配（GRASP）、依赖方向（领域不依赖框架）
|本项目共同点 |同一 HTTP 契约、同一数据库、同一组 HTTP 验收测试；启动时二选一 |同左
|===

结论：两者的区别不在“是否分层”，而在模型中心与变化边界：结构化以数据和步骤为中心，DDD 以领域概念和不变量为中心。

== GRASP 职责分配

=== API A：建立角色继承

[cols="1,2,3,2",options="header"]
|===
|原则 |对象 |为什么由它负责 |代码位置
|信息专家 |`RoleGraph` |只有角色图掌握全部继承边，由它判断新边是否成环、哪些路径有效 |`RoleGraph.assertCanInherit` / `effectivePaths`
|创建者 |`DddRoleGraphService`、`AuthorizationSnapshot` |它们持有构造 `RoleGraph` 所需的邻接快照，因此负责创建 |`DddRoleGraphService.validate`
|控制器 |`RoleHierarchyController` → `HierarchyUseCase` |系统事件“建立继承”的入口；Controller 不做业务判断，只委派用例 |`RoleHierarchyController.inherit`
|低耦合 |`DddHierarchyService` |只依赖 `RoleCatalog`、`AssignmentRepository` 端口，不依赖 JPA |`DddHierarchyService`
|高内聚 |`RoleGraph` |只负责图的不变量与遍历，不含持久化与 HTTP |`RoleGraph`
|多态 |`HierarchyUseCase`、`RoleGraphUseCase` |结构化与 DDD 两种实现由同一接口多态替换，按配置装配 |`@ConditionalOnProperty`
|纯虚构 |`JpaAssignmentAdapter`、`AuditTrailService` |持久化与审计不是领域概念，人为构造的类承担，保持领域纯净 |`infrastructure/persistence`、`service/audit`
|间接 |领域仓储端口 |应用服务与 JPA 之间加一层接口，隔离数据库 |`service/ddd/domain/repository`
|保护变化 |`app.backend-strategy` 与 `RoleGraphUseCase` |算法或设计路线变化不影响 Controller 与 HTTP 契约 |`application.properties`
|===

=== API B：接入应用查询当前身份

[cols="1,2,3,2",options="header"]
|===
|原则 |对象 |为什么由它负责 |代码位置
|信息专家 |`AuthorizationSnapshot` |它持有角色、继承图与角色授权，最适合计算有效角色和应用内有效权限 |`effectiveRoles`、`grantedIn`
|信息专家 |`ProtectedResource` |资源自己知道是否启用、是否登记权限码 |`authorityCode()`
|信息专家 |`ManagedSystem`、`Account` |应用启停、账号可用性由各自对象判断 |`getEnabled()`、`usable(now)`
|创建者 |`DddApplicationIdentityService` |它聚合了构造快照所需的全部数据，因此创建 `AuthorizationSnapshot` |`current`
|控制器 |`ApplicationIdentityController` |接入应用调用的入口，只做路径参数与身份映射 |`me`
|保护变化 |应用编码路径 `/api/apps/{code}` |课程系统只配置 `IDENTITY_BASE_URL`；新增接入应用不改代码 |`ApplicationIdentityController`
|间接 |`CurrentActorProvider` |审计服务不直接读 HTTP 请求，经端口取得操作人 |`RequestCurrentActorProvider`
|纯虚构 |`IdentityMapping` |HTTP 表现与用例结果的转换不属于领域 |`controller/identity/IdentityMapping`
|===

未采用的原则说明：两个 API 没有使用继承层次表达多态（如角色子类），因为角色类型由数据（编码与继承边）表达，用继承会把可配置的业务规则写死在代码里。

== 统一权限：课程项目管理系统接入

课程系统沿用老师仓库的统一身份契约，不改业务代码，只配置 `APP_IDENTITY_BASE_URL=http://rbac-backend:18081/api/apps/cpm`：

[cols="2,2,3",options="header"]
|===
|课程系统调用 |权限系统接口 |用途
|`GET {base}/auth/me` |`GET /api/apps/cpm/auth/me` |当前用户、角色编码、权限码；课程后端把权限码装入 Spring Security 做接口授权，前端按菜单/按钮码显示菜单
|`GET {base}/identity/users/{userId}` |`GET /api/apps/cpm/identity/users/{userId}` |添加教师时按统一身份标识查姓名与工号
|`GET/POST {base}/auth/audit-logs` |`GET/POST /api/apps/cpm/auth/audit-logs` |课程关键操作写入统一审计；课程端按可见范围查询
|登录（前端） |`POST /api/auth/login`（经课程前端 Nginx `/identity/api/auth/login` 转发） |课程前端补丁新增统一身份登录页，令牌存入 `cpm.accessToken`
|===

权限码模型：课程系统的前端菜单/按钮码（`MCO`、`MCOR` …）登记为 `cpm` 应用的前端权限；后端权限码（`TC`、`CV` …）登记在 API 资源的 `code` 上；两者经“前端权限—API”绑定，随角色（含继承）下发。课程应用的完整登记清单见 link:../../scripts/register-course-app.py[register-course-app.py]（只调用普通管理 API，可重复执行）。

== 日志设计

* `logback-spring.xml`：控制台始终输出；`swarm` 配置下另写滚动文件 `/app/logs/permission.log`（20 MB 滚动，保留 14 天）。
* 每行日志格式：`时间 级别 [请求号] [menu=前端菜单] [user=用户ID] 类名 : 内容`。
* `RequestLoggingFilter`：为每个 `/api` 请求分配请求号（同时写入响应头 `X-Request-Id`），记录“请求开始/结束、状态、耗时”；菜单取自前端每次请求携带的 `X-Client-Menu`，只接受简单标识，防日志注入。
* `ApiAccessConfig`：认证通过后把用户 ID 放入 MDC。
* `LayerLoggingAspect`：Controller、Service、DDD 应用服务 INFO，基础设施适配器 DEBUG；参数只输出数字、布尔、枚举与短字符串，密码、登录、令牌相关参数一律 `***`。
* 业务日志：角色继承建立/解除、接入应用身份查询、审计写入各有一条语义化 INFO 日志。

前端切换菜单时，`docker service logs -f cdwy_rbac-backend | grep "menu=hierarchy"` 即可看到对应请求经 Controller、Service 的完整日志。
