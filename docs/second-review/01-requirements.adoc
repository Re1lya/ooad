== 文档目的与范围

本文是统一权限管理系统在第二次课程设计检查（2026-11-24 至 11-26）时的需求基线，替代第一次检查时把 RBAC1 列为“范围外”的旧版本。
本轮必须完成：

. 分别用面向功能（结构化）与面向对象（DDD）方式实现 RBAC1 后端，并完成部分前端；
. 权限系统与课程项目管理系统的前后端全部部署到 Docker Swarm，两个系统的权限都由权限系统管理；
. 权限系统前端切换菜单时，后端产生对应的 logback 日志；
. 需求、测试、接口、UML 与代码可以相互对应。

== RBAC1 规则（组内确定的验收语义）

. 继承方向：高级角色 → 被继承角色；高级角色获得被继承角色的全部有效权限，可多级传递、可多继承。
. 拒绝角色继承自身，拒绝直接或间接成环；防环检查包含已停用的角色，避免重新启用后成环。
. 重复建立同一条继承边保持幂等；解除只删除这一条直接边，其他路径仍可提供权限。
. 用户最终权限 = 直接分配角色的权限 ∪ 沿启用路径可达的全部被继承角色权限，按权限 ID 去重；用户可有多个角色。
. 停用中间角色阻断经过它的路径，关系保留，启用后恢复。
. JWT 只携带身份与有效期，不携带权限快照；继承或授权变化在同一 Token 的下一次请求即生效。
. 前端区分“直接拥有”和“继承获得”，并展示一条最短有效路径。
. 角色继承的建立与解除写入审计记录（应用编码 `rbac`）。

== 功能需求

[cols="1,2,5",options="header"]
|===
|编号 |需求 |验收条件

|FR-01 |账号密码登录 |有效账号且 BCrypt 校验通过返回 Bearer JWT；错误、停用、过期账号返回 401
|FR-02 |本人身份与改密 |从 Token 确定主体；改密校验原密码，全部旧 Token 失效
|FR-03 |用户维护 |分页查询、新建、编辑、单独启停、管理员设置密码、删除；普通 DTO 不能修改管理员身份
|FR-04 |人员身份 |正式、外部、临时共用用户实体；外部/临时须设期限且不超过配置上限
|FR-05 |部门维护 |部门树防环；有用户或子部门时不能删除
|FR-06 |应用维护 |应用编码固定；单独启停影响该应用下全部权限与 API
|FR-07 |角色维护 |多个角色取并集；停用角色不计入有效授权
|FR-08 |前端权限树 |只有 MENU/BUTTON；按钮归属同应用菜单；父节点防环，祖先停用使后代无效
|FR-09 |API 资源维护 |应用 + 方法 + 路径唯一，独立启停；可登记后端权限码（如 `TC`、`CV`），同一权限码可覆盖多个接口
|FR-10 |用户角色分配 |M:N，重复分配幂等；撤回一个角色不影响其他角色提供的权限
|FR-11 |角色权限分配 |M:N，以节点为单位授权，不隐式扩散到子节点或祖先
|FR-12 |前端权限绑定 API |M:N，两端同应用；一个按钮可调用多个接口
|FR-13 |个人导航 |返回有效授权节点及其祖先容器（granted=false 的容器不获得接口权限）
|FR-14 |真实请求鉴权 |业务接口按应用、方法、路径匹配最具体的 API 资源，无完整授权链返回 403
|FR-15 |状态独立变更 |5 类对象使用独立 `/status` 接口；普通编辑夹带状态返回 400
|FR-16 |演示页面 |管理端维护基础对象与三组关系；个人端查看权限、改密、调用示例接口
|FR-17 |多级角色继承 |见第 3 节；撤除必要路径后下一次鉴权返回 403
|FR-18 |继承图一致性 |拒绝自继承与环；重复幂等；并发反向加边只成功一边；删除被引用角色返回 409
|FR-19 |有效来源解释 |权限去重并展示直接/继承来源与最短路径；停用角色阻断路径
|FR-20 |继承访问边界 |管理员维护继承与预览；普通用户只能查本人来源
|FR-21 |前端任务闭环 |资源管理、继承、三组授权、个人验证全部经真实 API
|FR-22 |交互可用性 |取消不写、错误可读、提交防重、退出清理身份、窄屏可操作
|FR-23 |RBAC1 核心双实现 |`structured`、`ddd` 条件装配；同一组继承验收在两种模式下通过；实际模式可查询
|FR-24 |员工信息同步预览 |管理员上传课程系统提供的员工信息表（XLSX），逐行校验并指出 Excel 行号；只返回变化摘要（部门、人员、补授角色）和文件摘要值，不写库
|FR-25 |员工信息同步确认 |文件与规则须和预览一致（否则 `SYNC_PREVIEW_MISMATCH`）；事务内建立“分公司 / 部门”两级树、新建人员（停用）并按分公司补授角色；按工号幂等，重复执行无变化；表中出现管理员账号时整批拒绝
|FR-26 |全业务双设计 |全部业务端口分别提供两种实现；领域层无 JPA 依赖；两种模式复用同一组验收
|FR-27 |接入应用身份查询 |`GET /api/apps/{应用编码}/auth/me` 以用户本人 JWT 返回 `{subject, roles, permissions}`：roles 含继承得到的角色编码；permissions 只含本应用的菜单、按钮码及其绑定的启用 API 权限码；应用停用时为空；授权变化下一次调用即生效
|FR-28 |统一身份人员查询 |`GET /api/apps/{应用编码}/auth/users/{userId}` 返回 `{userId, no, name}`；用户不存在返回 404 `IDENTITY_USER_NOT_FOUND`
|FR-29 |接入应用审计 |`POST/GET /api/apps/{应用编码}/auth/audit-logs`：写入按 requestId 幂等并保存操作人快照；按应用隔离查询；应用内无任何有效权限的用户不能查询
|FR-30 |继承变更审计 |建立、解除角色继承写入审计记录，管理员经 `GET /api/audit-logs?system=rbac` 查看
|FR-31 |接入应用登录 |`POST /api/apps/{应用编码}/auth/login` 不需要令牌，只返回 `accessToken`、`tokenType`、`expiresIn`；`systems` 必须包含当前应用（`LOGIN_TARGET_NOT_IN_SYSTEMS`）且都已登记（`LOGIN_SYSTEM_UNKNOWN`）；令牌只能用于 `aud` 中的系统
|FR-32 |接入应用退出 |`POST /api/apps/{应用编码}/auth/logout` 后本人已签发的令牌立即失效，重新登录可继续使用
|FR-33 |前端权限码校验 |`GET /api/apps/{应用编码}/auth/permissions/{permission}` 只返回 `allowed`；继承得到的菜单为真，后端 API 权限码与无关权限为假
|FR-34 |接口调用权限校验 |`GET /api/apps/{应用编码}/auth/api-permissions/{operationId}` 返回 `operationId` 与 `allowed`；未登记的 operationId 返回 404 `API_OPERATION_NOT_FOUND`；operationId 应用内唯一
|FR-35 |部门目录查询 |`GET /api/apps/{应用编码}/auth/departments` 逐层查询（不传 `parentId` 为根部门），分页结构 `{page, pageSize, total, items}`；上级部门不存在 404，没有授权 403
|FR-36 |部门人员查询 |`GET /api/apps/{应用编码}/auth/departments/{departmentId}/users` 按工号或姓名查询，字段不含联系方式；部门不存在 404 `IDENTITY_DEPARTMENT_NOT_FOUND`
|FR-37 |浏览器跨域 |按配置放行接入应用前端来源：预检允许 `Authorization` 与所需方法，未配置的来源被拒绝
|FR-38 |控制台内置目录 |启动时幂等登记控制台应用、11 个菜单、按钮与管理接口，被删掉的内置授权下次启动补齐；每个管理接口都登记访问规则，未登记的接口一律拒绝；菜单随后端授权动态显示；内置应用、内置管理员角色、内置菜单按钮与管理接口不能停用或删除（409 `CONSOLE_BUILT_IN`），已被停用的在下次启动时恢复启用，避免所有人被锁在控制台之外
|===

== 两条设计路线覆盖的用例

全部 11 个业务模块（登录、用户、部门、应用、角色、菜单按钮、API 资源、授权鉴权、角色继承、员工信息同步、接入应用身份）都有两种实现，HTTP 契约与数据库相同。
答辩时重点对照的两个 API：

[cols="2,3,3",options="header"]
|===
|API |结构化实现 |DDD 实现
|`PUT /api/roles/{seniorId}/inherits/{inheritedId}` |`RoleHierarchyService` + `StructuredRoleGraphService` |`DddHierarchyService` + `RoleGraph`
|`GET /api/apps/{code}/auth/me` |`ApplicationIdentityService` |`DddApplicationIdentityService` + `AuthorizationSnapshot` + `ProtectedResource`
|===

审计日志（`AuditTrailService`）与 JWT、路径匹配一样属于两种模式共用的技术服务，不进入核心业务模型。
